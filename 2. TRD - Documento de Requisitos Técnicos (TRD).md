Documento de Requisitos Técnicos (TRD)
Arquitectura y Especificación Técnica del Sistema

Este documento técnico describe la estructura de un sistema distribuido que prioriza el funcionamiento sin conexión a internet, diseñado para operar de manera segura y eficiente mediante tres componentes principales. Su arquitectura integra una aplicación móvil para trabajadores que resguarda las credenciales criptográficas en el hardware del teléfono, una herramienta para distribuidores equipada con una base de datos local cifrada, y un servidor central encargado de la coordinación general. El núcleo de su seguridad se basa en el uso de llaves criptográficas y códigos QR firmados, los cuales permiten validar la autenticidad de cada transacción de forma completamente autónoma en el dispositivo del repartidor. Finalmente, el procedimiento se completa mediante una estrategia de sincronización diferida que acumula los registros locales para enviarlos automáticamente al servidor principal tan pronto se restablece la conectividad, previniendo fraudes y duplicados.

--------------------------------------------------------------------------------
1. Arquitectura General del Sistema
El sistema consta de una arquitectura distribuida Offline-First compuesta por tres bloques principales:
Cliente Móvil Trabajador: App desarrollada en React Native / Flutter que interactúa con la API nativa de biometría (LocalAuthentication en iOS y BiometricPrompt en Android) para gestionar la clave privada en el chip seguro (Secure Enclave / TEE).
Cliente Móvil Distribuidor: App en modo escáner con motor de base de datos local SQLite (SQLCipher) para validación local de firmas FIDO2 y cola de eventos diferida.
Backend Central & API Gateway: Servidor en Node.js / Go / Python (FastAPI) conectado a PostgreSQL 15+ que actúa como Servidor de Relying Party FIDO2 (SimpleWebAuthn) y motor de sincronización de entregas.
--------------------------------------------------------------------------------
2. Especificación de Passkeys (FIDO2 / WebAuthn)
Estándar: FIDO2 / WebAuthn (Public Key Cryptography).
Algoritmo de Firma: ECDSA sobre curva P-256 (secp256r1 / ES256).
Almacenamiento de Clave Privada: Hardware Aislado (Secure Enclave en iOS, TEE / StrongBox en Android). La clave privada NUNCA abandona el teléfono ni se transmite al servidor.
Desafío (Challenge): Nonce criptográfico aleatorio de 32 bytes para prevenir ataques de reentrada (replay attacks).
Estructura del Payload QR Firmado:
{
  "wid": "UUID_TRABAJADOR",
  "ent": "UUID_ENTITLEMENT",
  "ts": 1729022400,
  "nonce": "NONCE_32_BYTES",
  "sig": "FIRMA_ECDSA_BASE64"
}
--------------------------------------------------------------------------------
3. Estrategia de Sincronización Offline-First
Descarga de Paquete Diario (Batch Download): Al inicio del turno, la App del distribuidor descarga un paquete JSON que contiene:
Padrón de trabajadores activos.
Registro de llaves públicas FIDO2 de cada trabajador (public_key).
Registro de derechos de combos para la fecha (daily_entitlements).
Validación Criptográfica Local: La App del distribuidor decodifica el QR, extrae la firma y la verifica utilizando la public_key almacenada localmente en SQLite.
Idempotencia y Cola Diferida:
Cada entrega genera un id único (UUIDv4) en la App del distribuidor.
Se inserta en la tabla local deliveries_queue con is_offline_sync = true.
Al recuperar señal, la cola se transmite vía HTTP POST en lote (/api/v1/sync/batch-deliveries).
La base de datos central ejecuta el índice único idx_unique_daily_claim UNIQUE (worker_id, entitlement_id) descartando duplicados silenciosamente.
--------------------------------------------------------------------------------
4. Seguridad y Cumplimiento
Cifrado en Tránsito: TLS 1.3 mandatorio en todas las comunicaciones API.
Cifrado en Reposo: SQLite local protegido mediante SQLCipher (AES-256).
Protección contra Replay Attacks: Validación de timestamp en QR (expiración máxima en 60s) + registro de nonce procesado.
